# 3.1.7 开发方案：DLC 来源兼容与官方 SRS 编译

2026-11-03 · PROPOSED / 暂定，暂不推进。用户已确认保留官方 CLI 自动选择 SRS 格式；仅授权将本方案与相关工程文档提交并推送 dev。包版本仍为 3.1.6，功能尚未实施；推送不代表接受全部方案或授权开发、合并、部署、发布。

## 1. 推荐结论

消费 DLC 原生构建后输出的 YAML，通过现有 SOURCE 多行输入指定链接和分类；JSON 链接保持原用法。Worker 解析选中规则、与 JSON/手写规则合并，沿用一次 revision/head CAS 保存以及可选 GitHub Actions SRS 编译。

不增加仓库连接表单、分类浏览器、异步来源任务或 Go 解析器。自己的规则仓库沿用 DLC 原生构建/导出方法，发布相同 YAML，替换来源链接即可。

SRS 交给官方 `sing-box rule-set compile`；不强制文件头为 5，不增加官方库写入 wrapper，不修改二进制头。纯域名规则生成 v2 是预期行为。编译器升级到已核验的稳定版本并校验下载摘要，不能把“格式自动选择”误解为每次任务自动下载浮动 latest 编译器。

## 2. 已确认事实与当前缺口

- 现有 JSON 导入只接受四类域名字段：domain/domain_suffix/domain_keyword/domain_regex，归一化、去重并与 manual 合并；不是任意 sing-box Headless Rule 导入器。导入器目前不严格校验顶层 version，新的契约必须补齐。
- 当前编辑器、保存出口和 compiler-source 固定生成/接受 v2；workflow 固定 sing-box 1.13.14。当前四类域名规则只需 v2；本版保持生成源 JSON 的兼容结构，不为了展示最新版本改成 v5。
- 现有 SOURCE 是一个多行 Textarea，底部已有 ResourceTime、周期 Select、删除按钮；无需改造成逐来源表单或新建页面。
- 当前规则或来源定义变化才抓取；仅备注、排序及无变化保存不抓取。周期字段没有自动刷新执行器；本版不暗中增加 Cron。
- 8 个现有测试文件、41 项通过，覆盖 JSON/任务/回调/兼容等既有行为。SRS 测试使用模拟字节，不能替代真实编译、反编译和客户端匹配检查。
- 2026-11-02 查询到 DLC 最新 Release 为 20261101074624，全量 YAML 资产约 3.58 MB，低于 5 MiB 单源上限。这是发布页大小，不是 Worker 解析内存或 CPU 实测；后者是实施前置门槛。

## 3. 资源方式比较

| 入口 | 能力与成本 | 本版选择 |
|---|---|---|
| 官方 Release 的 dlc.dat_plain.yml 链接 + 分类 | include/归属已由原生构建器展开，保留分类/属性；只需抓取和格式转换 | 推荐，完整覆盖官方分类 |
| 自建仓库导出的同格式 YAML | 自己维护上游同步和 data，Sing-Sub 只替换 URL；可仅导出所需分类减小文件 | 推荐，同一个入口 |
| master/data/<分类> 原始链接 | 可能含递归 include、过滤、归属；单个文件内容不足以完整还原分类 | 不支持；提示使用构建产物，不静默漏规则 |
| 仓库地址 + ref + 分类 | 需要仓库下载、可信构建代码、版本冻结、来源任务及回调 | 暂不实现，避免扩大保存语义 |
| dlc.dat / 压缩包 | 需要 protobuf 或解压；与 YAML 重复提供同类输入能力 | 暂不实现 |
| 展开 TXT | 官方只发布部分分类；再维护一套文本格式增加分支 | 暂不实现，可在自建仓库转换成 JSON/YAML |

官方默认链接：

```text
https://github.com/v2fly/domain-list-community/releases/latest/download/dlc.dat_plain.yml
```

也可使用带固定 tag 的 Release 链接或固定 commit 的 raw YAML URL。latest 表示下一次实际抓取时跟随更新，不在每次读取页面/订阅时重新下载。不自动推导同仓库其他文件，不要求 PAT，也不借用用户同步仓库凭据抓取来源。

## 4. 最小交互：复用 SOURCE，每行一个来源

```text
https://example.com/base.json
https://github.com/v2fly/domain-list-community/releases/latest/download/dlc.dat_plain.yml#google,google@ads,category-ads-all
https://example.com/my-dlc.yml#my-direct
```

规则：普通 HTTPS 链接继续表示 JSON；带 `#分类` 表示 DLC YAML，逗号分隔多个选择器，合并为并集。分类必须明确填写，不默认导入全库。`google` 选择该分类全部规则；`google@ads` 只选择带 ads 属性的规则。

- 每行一个 URL，同一规范化 URL 只出现一次；需要更多分类时在同一行追加，保留现有“重复 URL”错误模型。
- 选择器大小写归一、去重并保留首次顺序；允许合法分类名中的 `!`，不能把名称中的 `!` 当取反运算符。
- 首版每个选择器最多一个正向属性；`!cn` 可作为字面属性名，`@-cn`、多属性布尔表达式、通配符与整库选择暂不支持，必须明确报错。
- URL fragment 只是编辑输入语法。先解析为 URL 和 selectors，再以无 fragment 的 URL 执行原有 HTTPS/重定向/地址校验；不放宽通用 fetch 的 fragment 禁令，不把选择器当作请求参数发给上游。
- 不增加类型 Select、仓库/ref 输入或分类下载预览。只增加双语帮助文本和示例；现有 Accordion、Textarea、周期 Select、ResourceTime、Alert、保存状态、Modal 和 typed API 继续使用。
- 无论扩展名或 Content-Type 如何，有选择器就按 DLC YAML 校验，无选择器就按 JSON 校验；不尝试“JSON 失败就按 YAML”，避免错误输入被另一解析器意外接受。
- 缺少分类、未知分类、无匹配属性、空分类、非法语法，错误定位到来源行和选择器；失败保留草稿及旧正文，不自动退为整个分类。

交互成本：JSON 用户不增加步骤；DLC 用户粘贴一个链接并在末尾填写分类即可。分类发现使用上游目录/文档，第一版不抓取全量列表给浏览器做选择器。

## 5. 数据契约与转换

现有 `metadata.entities[path].editor.ruleset.sources` 仅增加可选 `selectors`，不另建文件或重复保存 raw 输入行。示意：

```json
{
  "url": "https://github.com/v2fly/domain-list-community/releases/latest/download/dlc.dat_plain.yml",
  "selectors": ["google", "google@ads"],
  "intervalHours": 0
}
```

selectors 缺省表示现有 JSON 来源；存在时必须为非空、去重并校验的数组，表示 DLC YAML。保存的 url 永远不含 fragment；编辑器读回时组合成来源行。`lastFetchedAt` 仍由服务端维护。来源身份为规范化 URL + selectors，改分类不能借用旧分类的成功抓取时间；只改周期保留时间。

选择器参与 editableMetadata 比较、规则编辑定义完整性校验、导入导出和同步 hash；不能在现有只 pick url/intervalHours 的路径中被丢弃。它只在 metadata 中出现，不进入公开 JSON、订阅或 SRS 编译源。缺省 selectors 是正常 JSON 来源模型，不引入另一套旧 schema 转换层。

输入接受上游 datdump 的两种已展开形状：

```yaml
lists:
  - name: "example"
    length: 1
    rules:
      - "domain:example.com:@ads"
```

```yaml
"example":
  - "domain:example.com:@ads"
```

第二种由上游 `datdump --exportlists=example` 生成，便于自己的规则仓库只发布所需分类。单个/多个分类映射采用相同白名单校验。全量形状的 length 必须为非负整数且与规则数相符；重复分类、重复键、未知结构和非字符串规则阻断，不使用长度字段跳过内容验证。

| DLC 已展开规则 | 合并字段 |
|---|---|
| domain:example.com | domain_suffix，匹配根域名及子域名 |
| full:example.com | domain，完整匹配 |
| keyword:example | domain_keyword |
| regexp:… | domain_regex，保留大小写、冒号、转义 |

属性采用原生导出的 `:@attr1,@attr2` 尾部格式，先完成属性筛选，再去掉管理属性。只在规则类型分隔符和合法属性尾部解析，禁止对整个正则直接 split(':') 或按原始 data 的空白语法解析。包含冒号、转义或 `:@` 的正则必须有对照测试；导出格式本身不能消歧时阻断，不能猜测后扩大匹配。已展开输入不得出现 include 或 & 归属；不在 Worker 递归补抓取。

JSON 来源校验 `version` 为受支持的 1–5 整数及规则对象白名单；所有规则仍限制为四类域名字段，不支持的字段完整拒绝。合并后生成域名专用 v2 JSON；版本 5 能力并不等于开放所有新字段。manual、各来源顺序和现有稳定去重规则不变，正则不经 JS 正则引擎重写。

## 6. Worker 与保存流程

```text
SOURCE 输入 → shared 解析来源描述 → typed API
→ application 刷新来源 → 公共 HTTPS fetch adapter
→ JSON 或 DLC YAML → 同一 RuleBucket 合并
→ 一次正文 + metadata revision/head CAS
→ 已启用时 dispatch 现有 SRS job → 官方 CLI → 原 callback
```

- 把现有 route 内的抓取/合并编排移到 application；route 保留认证、schema、use case 调用和响应映射。复用现有 fetch、重试、超时、重定向及大小限制，不搭建通用插件/解析器注册框架。
- YAML 拟采用 `yaml` 的 ISC 稳定版本作为直接 Worker 依赖；不得依赖工具链偶然存在的传递依赖，也不手写 YAML 子集解析器。只由 Worker 引入，shared/browser 只包含来源语法和 DTO。禁用自定义 tag、merge key 和 alias 展开，限制结构深度、分类/规则数及选择器数。
- 继续 5 MiB 单源上限；同次保存另设总下载预算初值 10 MiB，避免多个近上限来源无界堆积。顺序处理并及时释放 YAML 文档，构造 RuleBucket 只保留选中分类；不把全量上游文件塞进 revision。
- RULE-3171 必须在隔离 Worker 测量官方全量 YAML和总预算内多源的 CPU、峰值内存与超时。未达到部署实际资源限额就不能进入实现验收；不得静默放大上限。必要时优先让自己的规则仓库导出小文件，涉及改变默认接入方案时更新本计划。
- 保存开始先校验 expectedRevision；抓取后仍由 CAS 防止并发覆盖。任何来源失败都不发布正文/metadata/job；抓取时间只在整个保存成功后可见。
- 保持仅备注、排序、无变化保存不抓取、不编译；来源定义变化按既有保存策略刷新，重抓但正文相同不触发新 SRS。现有保存成功后派生构建失败不回滚 revision，仍保留旧 active artifact。
- 不启用 GitHub/SRS 时，DLC 依然能导入并公开 JSON；来源格式不依赖编译器配置。

## 7. SRS 编译器升级与产物身份

用户已确认采用官方 CLI 的自动格式选择。当前核验稳定版 1.14.4；实施时复核官方稳定版和校验摘要，并将具体编译器及摘要作为一次受审计升级固定到 workflow。现有 job.compilerVersion/回调版本校验仍有确定含义。不增加用户格式版本输入，不承诺每次产物都是 v5，也不强迫纯域名用户升级客户端到 1.14。

继续保留域名源 JSON v2；官方 CLI 可支持新格式，但本版不为虚假的“v5”标签增加无关规则。真实测试验证官方 CLI 读取 v5 域名测试源后自动生成 v2，以及读取生成物后规则语义一致。

编译器升级不能只改 workflow 常量：

1. reconcile 的 current/reuse 判断必须比较 compilerVersion，不能只比较 sourceHash；更新或重试不能复用旧编译器的 pending/failed job。
2. 新产物身份使用 sourceHash + compilerVersion，避免同一源在不同编译器下产生不同字节并撞上旧不可变 key。新 artifact pointer 可选记录 compilerVersion；新 key 统一由 r2ObjectKeys 生成。
3. 既有 pointer 缺少 compilerVersion 时继续按既有 sourceHash key 精确读取；不能按 build summary 的新 compilerVersion 猜测旧 active 的位置。该规则只用于已存在产物读取，不能用于新 job 写入或把旧 artifact 判作升级完成。
4. 构建失败/升级中仍可读旧 active；新成功产物原子激活。公开 URL、ticket 权限、哈希校验、CAS/superseded、retention 和备份边界不变；保留清理必须识别新旧 key，不能误删旧 active。
5. 现有 workflow provisioner 检查模板差异并更新；只有升级成功后才 reconcile/dispatch 新编译器任务，避免 Worker 与已安装 workflow 版本错配。保留人工开启/更新入口，不在只读请求自动改仓库。

## 8. 自有规则仓库的最小约定

规则仓库与 Sing-Sub 的私有同步/编译仓库是不同职责，不自动创建或绑定新仓库。用户维护自己的 data 目录，采用 DLC 原生构建器：

```sh
go mod download
go run ./ --datapath=./data --outputdir=./output
go run ./cmd/datdump --inputdata=./output/dlc.dat --outputdir=./output --exportlists=_all_
```

只需部分分类时将最后的 `_all_` 换成逗号分隔的分类名，生成按分类的 YAML 文件；上游代码以测试过的 commit 固定，数据更新由规则仓库自己的流程处理。Sing-Sub 仅消费发布的 HTTPS YAML，不执行该仓库代码。后续实施文档提供构建/导出示例；创建仓库、安装 workflow、发布资产及定时同步上游不属于本轮授权。
